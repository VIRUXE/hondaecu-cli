# ROM `check` Command Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `hondaecu-cli check <rom>` runs a ROM on a modelled P28 or P30 box wired to a described car and prints one verdict: worth burning, do not burn, or could not tell.

**Architecture:** One bench (`bench.rs`) owns the processor, the board and the scripted engine and logs only what is visible outside the chip. A fixed script (`script.rs`) drives it through key-on, cranking, idle, a full-throttle sweep and a code read-out; `verdict.rs` turns the log into three-state lines and `report.rs` prints them. The car and box are plain data (`car.rs`) applied to the board by `wiring.rs`.

**Tech Stack:** Rust 2024, the existing `hondaecu-cli` binary crate, no dependencies.

**Spec:** `docs/superpowers/specs/2026-11-13-rom-check-design.md`. Read it first; this plan argues from it.

## Global Constraints

- Branch `feat/rom-check` from `feat/datalog-protocol` at `fd87785`. That branch, not `main`, holds the current emulator (9 commits ahead).
- `[dependencies]` in `Cargo.toml` stays empty.
- ROM images are never committed. ROM-backed tests are opt-in through a cargo feature plus an environment variable, exactly like `p28-rom` in `src/fixtures.rs`: without the feature `#[ignore]`d with a reason, with it a missing file panics.
- Every `Ok` line in a result must come from an observed output of the executing ROM. No constant passes.
- A model is never adjusted to make an expected code appear. When the result disagrees with Honda practice, write the disagreement down in `docs/CHECK.md` and leave the model as the evidence supports.
- A value the user did not supply is listed in the report as defaulted.
- Three line states everywhere: `Ok`, `Problem`, `CouldNotTell`. An instruction the emulator does not implement is `CouldNotTell`; an opcode the processor does not define is `Problem`.
- Exit status: 0 clean, 1 problem, 2 bad command line or unreadable file, 3 could not tell and no problem.
- Search with `rg`, never `grep -r`.
- Build before using the CLI by hand: `cargo test --release` does not rebuild `target/release/hondaecu-cli.exe`; run `cargo build --release`.
- Test commands: `cargo test --release <filter>`; ROM-backed: `cargo test --release --features rom-fixtures <filter>`.

## Review Focus

1. **A blank or erased chip file** (32768 bytes of `FF`, or of `00`): the tool says "do not burn, never settles" and exits 1; it must not hang, loop forever or panic. Test in Task 2.
2. **A car file a person typed by hand**: quoted values (`o2_sensor = "heated"`), `#` comments, blank lines, Windows line endings and trailing spaces are accepted; an unknown key or bad value is refused naming the line number. Test in Task 3.
3. **Standard input ends in the middle of the questions** (piped input, Ctrl-Z): the remaining answers take their defaults and are reported as defaulted; no panic, no endless re-ask. Test in Task 9.
4. **The ROM path is wrong**: a missing file, a directory, or a file of the wrong size gives one sentence and exit 2, before anything runs. Test in Task 9.
5. **`--report` names a path that cannot be written**: the text verdict is still printed, the failure is reported on stderr, and the exit status is 2. Test in Task 9.

```rust
pub enum Lamp { Off, Steady, Codes(Vec<u8>), Unreadable }
/// `edges`: (seconds, lit) changes; `from`..`to` is the read window, opened when
/// the service connector was grounded. Codes are distinct, ascending.
pub fn decode(edges: &[(f64, bool)], from: f64, to: f64) -> Lamp;
pub const LONG_BLINK_MIN_SECONDS: f64;   // measured in step 1
pub const CODE_GAP_MIN_SECONDS: f64;     // measured in step 1
```
- A code is a run of blinks ended by a dark gap of at least `CODE_GAP_MIN_SECONDS`: tens = blinks lit for at least `LONG_BLINK_MIN_SECONDS`, ones = shorter blinks. A run cut off by `to` is discarded. - A section's state is `Problem` if any line is, else `CouldNotTell` if any line is, else `Ok`. The verdict takes the first `Problem` line in `valid` then `runs`, else the first `CouldNotTell`, else `WorthBurning`.
- `valid` lines:

| label | Problem when | CouldNotTell when |
|---|---|---|
| `executes` | `Stop::UndefinedOpcode` | `Stop::Unimplemented` |
| `settles after power-on` | `NeverSettles`, `ResetsLater` or `Hung` | settling is `Stopped` |
| `talks only to this board` | the board was never programmed | any unmapped access, or an unsupported 82C55 mode |

| label | Ok when |
|---|---|
| `fuel pump prime` | on for 0.5 to 5 s in `key on` and off at its end |
| `cranking` | every output opened at least once in `cranking` |
| `warm idle` | each output's openings within 2 of `engine_cycles`, and ignitions at least 3 per engine cycle |
| `idle, A/C on` | `ac_clutch_seen` (line absent without the stage) |
| `full throttle sweep` | always Ok or CouldNotTell: reports `fuel_stops_rpm` and `vtec_on_rpm`, or "fuel never stopped below 9000 rpm" |
| `check-engine light` | never lit after the bulb check |
| `codes` | `Lamp::Off`; `Codes` is a Problem listing numbers and names; `Steady` is a Problem "lit, no code blinked"; `Unreadable` is CouldNotTell |
